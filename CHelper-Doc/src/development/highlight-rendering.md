# 命令编辑器高亮渲染专项（长单行高亮拖动掉帧）

> **状态**：**维持原行为**（span 高亮全程可见；超长单行命令拖动掉帧为已知遗留）。两条试验路线均已试行并回退（详见 §3）。`setColors` 哈希 diff（O(段数)）等无行为变化的优化保留。
> 范围：仅安卓命令编辑器 `CommandEditText`；rawtext 编辑器 / 库页高亮文本短、段数少，不受影响。
> 关联：历史实现演进见 git（`ae42d312` 初始导入版 = 同色段合并 + span diff；`d2f5d0f8` 阈值可配置化「语法高亮自动关闭阈值」，默认 4000 字符，现设置项保留）。

## 1. 问题与约束

- Android `TextView` 对每个 span 边界切一个绘制段（TextLine）。大段 rawtext JSON（约 900+ 字符）高亮可达 **300+ 色段**；**单行模式**（maxLines=1 + 横向滚动）下整行所有段参与每帧绘制 → 拖动光标/拖选明显掉帧。
- **多行模式不卡**：取消横向滚动后长行自动折行，色段摊到多行，TextView 按行裁剪，每帧只绘可视行的少量段。
- 关闭高亮（无 span、单 run）拖动流畅——已实证瓶颈在"单行 × 段数"的系统级分段绘制，与 `setColors` 更新逻辑无关。
- span 数量 = token 颜色语义粒度，无法在不改变配色观感的前提下压缩；TextView 无"仅绘可见 span 段"能力。

## 2. 目标与验收（未达成，留存）

- 拖动光标/拖选期间**高亮全程可见**且不掉帧（与关闭高亮同帧率）；
- 打字/回填/主题切换/悬浮窗/主界面行为一致，无文本/光标/选区错位，输入法兼容。

## 3. 已尝试与结论（时间线）

| 尝试 | 做法 | 结论 |
| --- | --- | --- |
| 拖动摘除 + 分批恢复（2026-09） | 拖动/拖选时临时摘除高亮 span，停顿 220ms 后分帧恢复 | 回退：拖动中无色不可接受；恢复瞬间仍卡（一次性重建数百 span） |
| A 原型：透明文本 + onDraw 视口内自绘（2026-09） | 文本置透明（无 span、单 run）保拖动流畅；onDraw 只对当前视口内的色段 `drawText` 上色 | 回退：仍掉帧（自绘循环全段求 x 坐标开销 + 透明文本系统侧处理未省）；**着色与文本错位**——自绘坐标未对齐 TextView 内部 padding/scroll 变换 |
| B 压缩色段 | 未实施 | 备选（见 §4） |

## 4. 备选路线

### B. 压缩色段（近期成本最低）
1–2 字符的符号/括号小段与邻接段同色（如 `=`/`,`/引号并入邻近内容色），段数 335 → 60–100；观感有轻微变化，实现简单、可回退。可与任何方案叠加。

### A'. 自定义渲染重启（若做，先解坐标）
透明文本 + 视口内自绘的**坐标根因**：需复刻 TextView 文本绘制的变换链（compoundPaddingLeft / extendedPaddingTop / scrollX 平移，且与单行横向滚动、gravity 垂直居中相关）。先用"最小可见文本 + 若干基准色段"在真机核对 x/y 偏移，再进入性能调优（视口段二分，避免每帧全段求坐标）。

### C. 完全自绘编辑控件（远期兜底）
放弃 EditText，自管布局/光标/选区/IME/撤销/横向滚动，工程量最大。

## 5. 建议

1. 若近期想改善：先上 B 压缩色段，真机对比拖动帧率与观感（335→几十段后单行绘制可能达标）；
2. A' 仅在 B 不达标且愿意投入真机迭代时重启，第一步是坐标对齐的最小原型；
3. C 不在近期考虑。
